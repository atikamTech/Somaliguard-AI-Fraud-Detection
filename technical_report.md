# Somaliguard Technical Report

## 1. Project Summary
Somaliguard is a local, multi-service fraud detection demo project built with:
- Next.js frontend dashboard
- NestJS backend API
- FastAPI ML engine
- Scikit-learn model training pipeline

The system evaluates transaction inputs and returns:
- A classification (`SAFE` or `SUSPICIOUS`)
- A risk score (0-100)
- Human-readable reasons and narrative context

This report documents what is currently implemented in code and avoids unverified claims.

## 2. Scope and Objectives
The implemented objectives are:
- Build a full-stack fraud monitoring interface.
- Train and serve a machine learning model for baseline fraud classification.
- Add rule-based and behavioral logic on top of model output.
- Provide explainable outputs for UI display and PDF reporting.

Current scope is a local development environment with no production deployment configuration.

## 3. Dataset and Feature Set
### 3.1 Dataset Source
The dataset is generated by `src/generate_data.py` and saved to `dataset/somaliguard_transactions.csv`.

Generation script details:
- Creates 1,250 synthetic rows.
- Services sampled from `EVC_Plus`, `Sahal`, `Zaad`.
- Includes columns: `sender_id`, `service`, `amount`, `old_balance`, `hour`, `is_fraud`.
- Applies a deterministic fraud rule override: `is_fraud = 1` when `amount > old_balance`.

### 3.2 Model Features
Training and inference use three core numeric features:
- `amount`
- `old_balance`
- `hour`

Additional behavioral context is computed at API time in the ML engine (not part of model training), such as:
- Time gap from recent transactions
- Amount jump versus recent average
- Night burst patterns
- Multi-channel hopping pattern within a short time window

## 4. Model Training Pipeline
Training is implemented in `src/train.py`.

Pipeline behavior:
- Loads `dataset/somaliguard_transactions.csv`.
- Trains two candidates:
	- Logistic Regression with `StandardScaler` pipeline
	- Random Forest Classifier (`n_estimators=200`)
- Splits data into train/test using `train_test_split` (20% holdout).
- Computes holdout accuracy for both models.
- Selects the higher-accuracy model automatically.
- Saves selected model to:
	- `models/best_model.pkl`
	- `models/fraud_model.pkl` (backward compatibility)

Important note:
- Accuracy values are printed when training runs; they are not hardcoded in this report.

## 5. Inference and Decision Logic
The runtime ML engine is `ml_engine/app.py` (FastAPI).

### 5.1 Endpoints
- `GET /` health-style message
- `POST /predict` fraud analysis endpoint

### 5.2 Request Fields (Core)
- `amount`
- `old_balance`
- `hour`
- `service`
- `timestamp`
- `user_id`
- optional `history` (up to 2 entries)

### 5.3 Decision Composition
Final decision is not model-only. It combines:
- ML prediction and optional probability (`predict_proba`)
- Stateful cache per `user_id` (recent transactions)
- Rule checks (service amount limits, channel hopping, time-based penalties)
- Risk scoring logic that returns a 0-100 score
- Narrative generation for explainability

Response includes:
- `prediction`
- `risk_score`
- `fraud_probability` (if available)
- `reasons`
- `reason`
- `behavioral_features`
- `narrative`
- `velocity_multiplier`
- `value_jump`
- `channel_hop_blocked`

## 6. Backend Integration (NestJS)
The backend service (`somaliguard-backend`) exposes:
- `POST /fraud/check`
- `GET /transactions`

`POST /fraud/check` flow:
- Validates input amount.
- Adds runtime fields (`hour`, fixed demo `balance`, client-derived `user_id`).
- Calls Python engine at `http://127.0.0.1:8000/predict`.
- Returns normalized response used by the frontend.

`GET /transactions` currently returns static sample data from `transactions.service.ts`.

## 7. Frontend Capabilities (Next.js)
The dashboard (`somaliguard-frontend/app/page.tsx`) implements:
- Real-time transaction scan submission
- Risk visualization and status indicators
- Intelligence feed with AI narrative tags
- Simulation panel for normal and suspicious patterns
- PDF export via `jspdf` and `jspdf-autotable`

This UI is designed for interactive demonstration and operator-facing explainability.

## 8. Current Limitations
- No persistent database integration for transaction history.
- No authentication or role-based access control.
- No automated model retraining schedule.
- No containerization or production infrastructure files.
- Backend currently includes demo/static transaction endpoint.

## 9. Conclusion
Somaliguard currently functions as a complete local prototype that demonstrates:
- End-to-end fraud classification flow
- Hybrid ML + rule-based risk analysis
- Explainable decision output in both UI and report formats

The project is technically solid for academic demonstration and further extension.
Recommended next phase is production-hardening: database persistence, auth, CI tests, model monitoring, and deployment automation.
